# 排球检测抽帧间隔验证报告

> 目的：验证上游性能优化中的 `BALL_INTERVAL`（每 N 帧检测一次排球）是否影响动作计数与评分
> 方法：同一段视频取 4 个不同起点、各 120 帧，分别用间隔 1 和 2 运行（只评分模式，不写视频）
> 日期：2026-09-14

---

## 一、实验数据

| 素材 | 间隔=1 动作数 | 间隔=1 平均分 | 间隔=2 动作数 | 间隔=2 平均分 |
| ---- | ---- | ---- | ---- | ---- |
| interval_clip_0 | 3 | 89.02 | 3 | 89.55 |
| interval_clip_1 | 5 | 87.08 | 1 | 94.54 |
| interval_clip_2 | 3 | 77.66 | 1 | 78.59 |
| interval_clip_3 | 4 | 86.83 | 1 | 87.44 |

- 平均分最大差异：**7.46 分**
- 动作数最大差异：**4 个**（第 2 段素材：5 → 1）

## 二、结论

1. 上游注释"N=2 时动作数与得分与原实现一致"**只在单段素材上成立**；
2. 在 4 段不同素材上，间隔=2 会**明显少算动作**，因为跳帧期间球的位置靠轨迹外推，动作区间容易被提前截断；
3. 因此本项目默认策略调整为：

| 场景 | 默认间隔 | 说明 |
| ---- | ---- | ---- |
| 离线视频分析 | 1 | 精度优先（`VB_BALL_INTERVAL_VIDEO=1`） |
| 实时分析 | 1 | 默认与离线一致，保证计数准确（`VB_BALL_INTERVAL=1`） |
| 性能不足时 | 2 | 可手动设置，但必须接受动作数偏差 |

4. 性能优化仍保留：二进制帧传输、异步写盘、逐帧推理线程池、GPU/FP16（CUDA 环境）。

## 三、顺带发现并修复的问题

1. **跨视频状态污染**：同一个进程连续分析多段视频时，上一段的排球轨迹历史（`volleyball_history`、`last_velocity`、`missed_frames_counter`）会污染下一段，导致偶发的绘制/计数异常。
   → 新增 `analyzer.reset_tracking()`，在每次视频/图片/实时会话开始前统一重置。
2. **排球框坐标类型**：`draw_volleyball_results` 对检测框坐标做 `int()` 强制转换，避免 OpenCV 因坐标类型报错。
